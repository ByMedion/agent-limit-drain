# `collect_codex_observation.py` — результаты проверки ревью (2026-08-20)

Это рабочий документ для code-контрибьютора: внешнее code review скрипта, каждый пункт
которого проверен на реальных Codex rollout logs и на синтетических прогонах `main()`.
Реализацию и обоснования проектных решений см. в
[collect_codex_observation.md](collect_codex_observation.md) — здесь только то, что
расходится с текущим кодом.

Документ фиксирует состояние на 2026-08-20 и не является планом изменений: часть
пунктов требует решения о семантике observation, а не правки.

## База проверки

Локальные логи одной машины: 188 rollout-файлов, 83 106 записей, 13 974 события
`token_count` (13 085 доходят до `Reading`), суммарно 240 MB, диапазон 2025-09 … 2026-08.
Тесты в исходном состоянии: `Ran 24 tests ... OK`.

Наблюдаемые в этих логах форматы:

| Период | `primary` | `secondary` | `limit_id` | `resets_at` | `plan_type` |
|---|---|---|---|---|---|
| 2025-09 | нет `rate_limits` | — | нет | — | — |
| 2025-11 … 2026-01 | 300 (5h) | 10080 | нет | нет, есть `resets_in_seconds` | `null` |
| 2026-02 … 2026-07-14 | 300 (5h) | 10080 | есть | есть | `null` → `"plus"` с 2026-03 |
| с 2026-07-14 | 10080 (weekly) | отсутствует | есть | есть | `"plus"` |

## Вердикты по пунктам ревью

### 1. Unknown model/reasoning может быть приписан известному значению — недостижимо

Из 13 085 распарсенных readings ни одна не имеет `model=None` или `reasoning=None`;
файлов, где `token_count` встречается до первого `turn_context`, — ноль. Причина
структурная: формат без `turn_context` (CLI 0.46.0) не содержит и `limit_id`/`primary`,
поэтому его readings отбрасываются раньше. Наследование
`model = payload.get("model") or model` легитимно — `turn_context` пишется на каждый turn
перед `token_count`.

Fail-closed при `None` осмыслен как defense-in-depth против будущей смены формата,
но текущий эффект нулевой.

### 2. plan_type не проверяется на однородность — дыра есть, но сейчас бессмысленна

Синтетический прогон (`plus, plus, pro, pro` внутри одного окна) выдаёт чистую CSV-строку
с `plan=pro` без единого предупреждения.

Однако проверять сейчас нечего: код читает поле не оттуда — см. **N1**. Сначала N1,
потом проверка однородности; `--plan` при этом должен перекрывать отсутствующие значения,
но не два разных non-null.

### 3. window_minutes не проверяется на однородность — дыра есть, на живых данных замаскирована

Тот же синтетический прогон с `10080, 300, 300, 10080` молча выдаёт `limit_type=weekly`.

На реальных логах смена `window_minutes` всегда сопровождается скачком `resets_at`, и
первой срабатывает reset-проверка — воспроизведено на двух настоящих окнах через
2026-07-14. Fail-closed держится, но **диагноз неверный**: пользователь читает
«the limit reset inside this window», хотя на деле сменилось само окно лимита.

### 4. Ручной `--start`: baseline и токены из разных интервалов — опровергается

Baseline по построению есть последняя reading `<= start`, а токены живут только в
readings. Значит в интервале `(baseline.ts, start]` token-событий нет вообще, и
`tokens_m` с `limit_used` покрывают один и тот же набор залогированных событий. Пример из
ревью (reading в 12:00, `--start` 13:00) не теряет токенов — между ними их физически нет.

Что остаётся реальным:

- в CSV пишется `start.date()` от *запрошенного* `--start`, тогда как измерение фактически
  начинается с baseline; разрывы между readings доходят до 13 д 23 ч (медиана 7.5 с), так
  что метка даты может врать на дни;
- незалогированный расход в этом промежутке (другое устройство, вычищенные логи) попадёт
  в `limit_used`, но не в `tokens_m`.

Направление: выводить эффективный start и предупреждать о большом отрыве baseline —
не перепривязывать сумму токенов.

### 5. Missing `resets_at` — проблема есть, предложенное направление неверное

Все 158 readings без `resets_at` несут `resets_in_seconds`. Восстановление
`resets_at = timestamp + resets_in_seconds` даёт дрейф max 50 с, p95 19 с; **0 из 157**
соседних пар превышают текущий `RESET_JITTER_TOLERANCE_SECONDS` (300 с).

То есть ужесточать отказ не нужно: поле выводится, и unconditional-проверка начинает
покрывать 100% readings вместо 98.9%.

### 6. Шумной endpoint — живая проблема

В текущем окне 4 допущенных провала: 5.0, 3.0, 1.0 и **8.0 п.п.** (88% → 80% за 2.4 с,
затем возврат к 91%). Сегодня не повредило: последняя reading = 92 = максимум окна. Но
`--end`, попавший внутрь 8-пунктового провала, занизил бы `limit_used` на ~9%
относительных.

Monotonic envelope по логам проверить нечем (нет доступа к серверной метрике). Минимальный
честный шаг — предупреждать, когда `end_reading.used_percent < max(used_percent)` в окне.

### 7. Молчаливые потери парсера — реальны, масштаб сейчас мал

Всего отброшено 36.5M из 1254.6M токенов (2.9%); за последние 60 дней — 0.32M из 637.7M
(**0.05%**). Почти вся потеря приходится на формат до 2026-02, где нет `limit_id`.

Причины нужно разделять:

- `no primary` / `no limit_id` — несовместимость формата целой эпохи, это надо сообщать
  громко, а не пропускать через `continue`;
- `info: null` — легитимные rate-limit-снимки без расхода токенов (см. **N5**);
- `JSONDecodeError` — отдельный баг (см. **N2**).

Диагностические счётчики из ревью — правильное направление. Замечу: потери занижают
`tokens_m`, то есть направлены **противоположно** задокументированному расхождению +2.7%
с UI, и его не объясняют.

### 8. Чтение файла целиком — приоритет выше, чем «низкий»

Замер на этих логах: пик RSS **349 MB → 34 MB**, и потоковый вариант ещё и чуть быстрее
(0.94 с против 1.17 с). Главное же — `read_text().splitlines()` теряет валидные записи,
см. **N2**.

### 9. DST/timezone — подтверждается

`LOCAL_TZ` = `datetime.timezone(timedelta(seconds=7200), 'CEST')` — фиксированный офсет без
правил IANA: наивный зимний `--start` получит `+02:00` вместо `+01:00`. Тот же дефект у
`format_resets_at()` — исторические reset-времена печатаются в текущем офсете.

Направление: `zoneinfo` по имени зоны либо требование явного офсета во входных данных.

### 10. Решения, которые не следует менять — подтверждается

Возражений нет. Побочно: текущее окно воспроизводит ровно задокументированные 197.7M,
а любое исключение replay-событий может только уменьшить `tokens_m`, то есть увести его
дальше от UI, а не ближе.

## Найденное сверх ревью

### N1. `plan_type` читается не оттуда

Поле лежит в `rate_limits.plan_type`, а код читает `primary.get("plan_type")`
(`collect_readings()`). В `primary` оно `null` во всех 13 974 событиях; в `rate_limits` —
`"plus"` во всех 8 101 reading начиная с 2026-03, включая все 1861 reading текущего окна.

Следствие: **каждый** прогон печатает «plan_type is not present in these logs» и оставляет
поле `plan` в CSV пустым, хотя значение есть в логе.

В [collect_codex_observation.md](collect_codex_observation.md) поле тоже описано в разделе
«Inside `payload.rate_limits.primary`» — доку править вместе с кодом.

### N2. `splitlines()` рвёт валидные записи

В файле `rollout-2026-07-26T02-34-35-…jsonl` есть два символа U+2028 внутри JSON-строк.
`read_text().splitlines()` режет по ним: 2513 корректных записей + 4 нечитаемых обрывка,
которые молча съедает `except json.JSONDecodeError: continue`. Тот же файл через
`for line in f` даёт все 2515 записей.

Сегодня потеряны не `token_count`, но механизм общий: `splitlines()` делит строку и по
U+2028/U+2029/U+0085/`\v`/`\f`, которые легитимно встречаются внутри JSON-строк.

### N3. `limit_id` — это не «аккаунт»

Второй `limit_id` в логах — `codex_bengalfox` с `limit_name: "GPT-5.3-Codex-Spark"`. Он
идёт вперемешку с `codex` **в одном и том же rollout-файле**, миллисекунды подряд, и в 411
из 411 таких пар `last_token_usage` идентичен. За февраль: `codex` — 422.6M токенов и
`used_percent` 0→48%, `codex_bengalfox` — те же 81.9M токенов при `used_percent`, не
сдвинувшемся с 0.0% ни разу.

Следствия: формулировка «multiple accounts found» в ошибке и «more than one ChatGPT
account/workspace» в доке неверны — это модельный пул лимита на том же аккаунте. Прогон с
`--limit-id codex_bengalfox` построил бы observation из чужих токенов; спасает только
проверка `limit_used <= 0`.

### N4. `secondary` не используется, из-за чего эпоха до 2026-07-14 непригодна для weekly

До 2026-07-14 weekly-данные лежат в `secondary`, а `primary` — это 5h. Значит на старых
логах скрипт в принципе может дать только `rolling_5h`, и практически не даёт ничего:
5-часовой reset обрывает любое окно длиннее 5 часов (проверено на двух реальных окнах).

### N5. События `info: null` отбрасываются

32 события: это rate-limit-снимки без расхода токенов (например, ровно в момент сброса
2026-07-28T18:56, `up=0.0`) — готовые baseline-точки. Их место — в выборке с
`turn_tokens=0`, а не в мусоре.

### N6. `used_percent` целочисленный

13 827 из 13 827 значений целые. `limit_used` несёт ±1 п.п. квантования на каждом конце;
в текущем окне 1 п.п. ≈ 2.15M токенов. Для датасета, у которого зависимая переменная —
drain factor, это стоит задокументировать явно.

### N7. `rate_limits.credits` есть в логе

`{"has_credits": false, "unlimited": false, "balance": "0"}`. Evidence-блок при этом
печатает хардкод «Purchased/additional credits used: No (verify manually)» — лог отвечает
на этот вопрос сам.

## Приоритеты

1. **N1** (plan читается не оттуда) и **N2** (потоковое чтение как фикс потери записей) —
   однозначные баги с готовым решением.
2. **N4 / N3** — вопросы семантики: решить, что такое observation при `primary`=5h и при
   модельном пуле лимита, и переписать соответствующие сообщения и доку.
3. Пункт **5** через `resets_in_seconds`; пункт **3** (проверка однородности
   `window_minutes` + честный диагноз); пункт **7** (счётчики + громкая ошибка при
   несовместимом формате).
4. Пункт **4** (эффективный start вместо перепривязки токенов), пункт **6**
   (предупреждение о неполном максимуме), пункт **9** (`zoneinfo`/явный офсет),
   пункты **1**/**2** (fail-closed как defense-in-depth).
